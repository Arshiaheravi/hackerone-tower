# Source contracts and decisions

Official sources reviewed for this implementation (2026-11-02):

- [Hacker API getting started](https://api.hackerone.com/getting-started-hacker-api/): overall reads 600 requests/minute; structured scopes 50/minute. Tower uses lower budgets and honors cooldowns.
- [Personal API token](https://docs.hackerone.com/en/articles/8410331-api-token): personal account username plus token value.
- [Hacker resources](https://api.hackerone.com/hacker-resources/): program list/detail, structured scopes and exclusions. Scope ID cursors support collections beyond the 10,000-item page cap. Updated-since filters cannot detect removals; Tower performs full reconciliation.
- [Hacker reference](https://api.hackerone.com/hacker-reference/): `public_mode`, public field allowlists, scope eligibility and dates. Program `started_accepting_at` is not labelled a public launch date.
- [HackerOne webhooks](https://api.hackerone.com/webhooks/): program-owned webhooks do not offer ordinary hackers a global program/scope feed. Tower polls.
- [Telegram Bot API](https://core.telegram.org/bots/api): `sendMessage`, `getUpdates`, `getMe`, message lengths and retry parameters. Plain text avoids interpreting source instructions as markup. Sends have no idempotency key.
- [Telegram reply keyboards](https://core.telegram.org/bots/api#replykeyboardmarkup): text-only buttons and persistent keyboard metadata are attached to private command replies. The adapter rejects contact, location, web-app and other button capabilities; no new Telegram permissions are requested.
- [Telegram FAQ](https://core.telegram.org/bots/faq): broadcast/per-chat limits and bot conversation setup.
- [HTTPX timeouts](https://www.python-httpx.org/advanced/timeouts/): bounded requests. Tower disables environment proxies, redirects and HTTP logging.
- [Python SQLite](https://docs.python.org/3.11/library/sqlite3.html): transactions and consistent backups.
- [Windows logon triggers](https://learn.microsoft.com/en-us/powershell/module/scheduledtasks/new-scheduledtasktrigger): logged-in account operation, not independent hosting.

HackerOne's [community terms](https://www.hackerone.com/terms/community) and [commercial community terms](https://www.hackerone.com/terms/CCM) contain access, third-party-use, extraction and licensing restrictions. They do not establish permission to resell this feed. Confirm applicable redistribution/commercial permission before public or paid launch. Tower does not accept payments or connect to any listed asset.

Intentional limits: no unofficial scraping fallback, private program contents, fabricated reward amounts, competition estimates or vulnerability probabilities. Unavailable fields remain unavailable. Contracts and terms can change; validate current documentation before release.

## Coverage improvement research — 2026-11-05

The official [Hacker API limits](https://api.hackerone.com/getting-started-hacker-api/) still specify 600 reads/minute and 50 structured-scope requests/minute. Two workers share Tower's existing lower budgets; adding workers does not multiply the allowed rate. At 40 scope requests/minute, even 595 one-page programs need roughly 14.9 minutes of scope-request capacity, before additional pages and network delays. This is a calculated capacity estimate, not a promised rotation time.

[Native program notifications](https://docs.hackerone.com/en/articles/8404255-notifications) cover subscribed programs' guidelines, bounty tables, scopes and hacker messages through email and the HackerOne interface. They can complement this monitor, but account/email access and subscriptions are needed. They are not integrated here, and account notifications must never be forwarded raw into a public feed. [Webhooks](https://docs.hackerone.com/en/articles/8588351-webhooks) are permission-bound, program-level integrations; the documentation does not offer this hacker account a global public-program change stream.

The [Directory](https://docs.hackerone.com/en/articles/8410373-directory) includes organizations that do not use HackerOne. [Opportunity Discovery](https://docs.hackerone.com/en/articles/8369900-opportunity-discovery) includes account-specific opportunities. Neither count establishes how many public API programs should be available. Third-party scope lists can also lag or omit entries; agreement between such lists would not prove complete coverage.

The [structured-scope endpoint](https://api.hackerone.com/hacker-resources/#get-structured-scopes) supports date filters, but incremental reads alone cannot establish which earlier assets were removed. Tower retains complete paginated reconciliation for deletion detection. A future incremental path would need overlap, deduplication, complete reconciliation and separate last-change/last-full-check dates before it could replace any full reads.

The measurable objective is **at least 99% of API-visible public programs checked within the freshness window**: the greater of 30 minutes and twice the configured scope refresh interval. Missing snapshots count against the denominator, inactive programs do not, and an empty catalog reports no percentage. This is a current freshness measurement, not detection recall or an uptime guarantee. A sustained objective requires observations over time; a single passing check cannot certify a month of reliability.

Live response-shape observation on 2026-11-02: the program detail endpoint returned a bare resource (`id`, `type`, `attributes`, `relationships`), whereas program and scope collections used a `data` envelope. Scope exclusions also used `data`. The adapter accepts both bare and wrapped **program details**, then validates resource identity, public visibility, and allowlisted fields. Collections still require a `data` list; a bare object is never interpreted as an empty or complete collection. This corrects the initial assumption that every endpoint shared the same envelope. Diagnostics recorded shapes only, without retaining response values or credentials.

Live pagination observation on 2026-11-04: a public program advertised 110 scope pages, but an isolated request for `page[number]=100&page[size]=100` returned HTTP 400. Page 99 succeeded, and restarting from its final scope ID with `filter[id__gt]` returned larger, ascending IDs; the returned next link preserved that cursor. The [structured-scope documentation](https://api.hackerone.com/hacker-resources/#get-structured-scopes) describes the 10,000-record ceiling and ID filtering, but does not specify this exact boundary. Tower switches cursor windows before reaching the observed ceiling. This boundary is a live observation, not a claim that the documentation guarantees page-99 semantics forever.

Accuracy follow-up on 2026-11-05: an offline reproduction showed that deleting a row before the next page-number offset can skip a still-present asset, producing a false removal. The documented ID ordering and `filter[id__gt]` allow every scope page to seek after its last observed ID instead. Tower now uses that strategy for all scope pagination, superseding the earlier boundary-only switch. A regression fixture verifies that surviving ID 101 is retained after ID 1 disappears between pages, and a newly appended ID is observed once. Exact multiples of 100 scopes require one extra empty-page probe. Already-read entries can still change during a traversal, so the next complete reconciliation remains necessary. This fixes a demonstrated error class; it does not establish a universal accuracy percentage.
